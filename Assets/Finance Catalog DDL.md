## Conventions

**Types.** `DECIMAL(19,5)` for currency amounts, `DECIMAL(19,7)` for exchange rates, `DECIMAL(9,6)` for ratios. Never `DOUBLE` for money — a float amount will not reconcile to GP and the difference gets blamed on the mapping rather than on the type. Dates are `DATE`, timestamps `TIMESTAMP`, GP's coded integers stay `INT` with the decode carried in a named column beside them.

**Surrogate keys are deterministic hashes, not identity columns.** Every `*_key` is a `BIGINT NOT NULL` populated by `xxhash64(natural key)`, with the derivation written into the column comment. `GENERATED ALWAYS AS IDENTITY` was rejected for two independent reasons: these tables are rebuilt from an overwrite-only replica, so identity would renumber on a full reload and orphan anything already keyed to it; and Delta identity columns cannot be populated by CTAS, which would constrain the load pattern for no benefit.

**`legal_entity_code` is in every natural key.** `ACTINDX`, `CUSTNMBR`, `JRNENTRY`, `BUDGETID` are unique *within* a GP company, not across companies. APFM and CAPFM are two companies. A key without the entity silently merges two counterparties.

**Constraints are informational.** Databricks does not enforce PK/FK; they are declared for the optimizer and for the reader. **No `RELY` appears anywhere** — `RELY` tells the optimizer to trust uniqueness it cannot check, and every candidate key here is still marked as needing a uniqueness test. Add `RELY` after the test passes, not before.

**`CLUSTER BY` on the natural query path**, max four columns, never combined with `PARTITIONED BY`. Usually `(legal_entity_code, …)` because almost every finance question is scoped to one company.

**Tags carry the properties a consumer needs before they write a query**: `grain`, `history_type`, `measure_class`, `cardinality`, `unions`, and — the ones that matter most — `excludes_source_columns`, `never_use_as_spine`, `do_not_reconcile_to`, `publication_blocked_on`.

**Audit columns on every table.** `_loaded_at` is when this pipeline wrote the row. `_source_synced_at` carries Fivetran's `_fivetran_synced` **for provenance only** — it advances only when a row changes, so it is not a freshness signal. Freshness is the connector's `succeeded_at`.

### GP quirks encoded in the DDL rather than left to the loader

| Quirk | Handling |
|---|---|
| Blank-date sentinel `1900-01-01` | `nullif(date(col), DATE'1900-01-01')`, noted on every date column |
| `char` columns are space-padded | Trim before joining; an untrimmed join to IPR or the YGL mapping returns nothing, silently |
| `DECPLCUR` / `DECPLACS` are **one-based** offsets | `3` means 2 decimal places. Carried as a column with the caveat, never applied blind |
| `SERIES` codes | `1 All, 2 Financial, 3 Sales, 4 Purchasing, 5 Inventory, 6 Payroll - USA, 7 Project` — decoded into a named column |
| Account segments | Read `SY00300.SGMTNUMB` / `MNSEGIND` and `SY01500.ACSEGSEP`. Do not assume five segments, do not assume which is the main segment, do not hardcode a hyphen |
| Two different delete concepts | `_fivetran_deleted` (tombstone, removed by the guarded layer) and GP's own `DELETE1` (kept). Both must be considered |
| GP's own typos | `GL32000.BudgerAdjustment`, `GL32000.REFRENCE`. Reproduced verbatim — a load script written from the corrected spelling fails, and the failure looks like a missing column |

## The one thing with a deadline

`snap_period_close_daily` in [03](ddl/03-common-calendar.sql). `SY40100.CLOSED` is a current-state boolean and Fivetran overwrites it. GP records "is this period closed now" and never "was it closed as of last Tuesday" — which is the question nine BO 2.0 vintage revenue measures actually depend on. **Every day without a snapshot is a day of history that cannot be recovered.** Start it collecting into a scratch schema before the catalog exists and before Finance reviews anything; the review can change the shape of the table later, but it cannot recover a day that was not captured.

Note the contrast with `snap_ar_aging_daily`, which is worth building for cost rather than for recoverability — see the correction below.

## Layer notes

**Guarded views** ([02](ddl/02-guarded-gp-views.sql)). `_fivetran_deleted` tombstones are 16% of the estate and 82–99.9% in the hot tables; omitting the filter overstates `gl20000` by roughly 5.7× and nothing in the query looks wrong. Named `_live`, not `_safe` — "safe" implies a privacy guarantee these views do not provide; they solve exactly one problem. Two limits are stated in the file header: they do not address freshness, and `SELECT * EXCEPT (...)` **pins the column list at creation time**, so a Fivetran-added column will not appear until the view is regenerated. The file ends with an `information_schema`-driven generator that covers all 59 physical GP tables rather than the documented 32, and that skips any table replicated without the tombstone column instead of failing on it.

**`common.calendar`** ([03](ddl/03-common-calendar.sql)). `dim_date` is written as a **promotion with the column list deliberately not restated**. There are already at least three copies — `main.prod_refined.dim_date` feeds `main.prod.dim_date` (nine downstream consumers) and `main.prod_edw_dbo.dim_date` exists too. Inventing a column list here would create a fourth definition while claiming to prevent one. `DESCRIBE` first. The deprecation statements for the three existing copies are present and marked **DO NOT RUN YET**.

**`finance.reference`** ([04](ddl/04-finance-reference.sql)). `dim_currency` and `fact_exchange_rate` are built to the shared-design contract now, so the expected move to `common` is a rename and a grant rather than a remodel. `dim_legal_entity` records a correction: the GL company account segment is `10` on 100% of APFM activity — all 8,204,550 rows, FY2000–2026 — so it is degenerate *within* an entity and no hierarchy should be built on it, but APFM and CAPFM are two replicated companies and therefore two real members.

**`finance.identity`** ([05](ddl/05-finance-identity.sql)). `dim_customer` is the **billing-account view of a partner**, not a partner master and not a family: GP's customer resolves at `business_unit_id` grain — a community — and `bridge_customer_to_business_unit` is effective-dated, which is the evidence. Type 1 by force, not by choice. The family bridge is built from `ipr` alone and **must not be routed through YGL**. Coverage is modelled as data (`coverage_era`, `is_spine_resolved`, `match_status`) rather than documented as a caveat, so a consumer aggregating across eras sees the discontinuity instead of averaging through it.

**`finance.general_ledger`** ([06](ddl/06-finance-general-ledger.sql)). `dim_gl_account` denormalizes all five segment code / name / description triplets, because a Genie agent answers far better against a flat named column than against a join it has to discover — and because `GL00105` is not replicated, so this dimension substitutes for it. `fact_gl_posting` unions `gl20000` and `gl30000`, reconciling `OPENYEAR` with `HSTYEAR`. BBF and P&L-close markers are **flags, not filters**: excluding them is right for activity reporting and wrong for an audit extract.

**`finance.receivables`** ([07](ddl/07-finance-receivables.sql)). See the correction below. Also note `mart_writeoff`: it is servable today, from `fact_ar_apply.WROFAMNT` with a date, and needs **no new ingestion** — a table and a grant. That is the stated CAM / Community Ops visibility gap closed with data that is already replicated.

**`finance.billing`** ([08](ddl/08-finance-billing.sql)). Nothing is named revenue and every table is tagged `measure_class = operational_not_recognized`. The moment a column here is called revenue, someone reconciles it to the income statement and it does not tie — because the two measure different things at different times, not because either is wrong. This is also where profiling is most outstanding: the IPR and CST tables are not in the GP reference, so every column not confirmed by the spine validation is marked `PROFILE`.

**`finance.plan`** ([09](ddl/09-finance-plan.sql)). `budget_id` is part of the grain — GP permits many budgets per year and summing across them produces a meaningless total. `mart_plan_vs_actual` is a **full outer join**: an account with spend and no plan is exactly what a variance report exists to surface, and an inner join hides it. Actual is sourced from `mart_account_period_activity` rather than from `fact_gl_posting`, so the two products agree by construction rather than by coincidence.

**Grants** ([10](ddl/10-grants.sql)). Unity Catalog inherits privileges *downward*, and there is no wildcard for "the unprefixed schemas." So `USE CATALOG` is the **only** catalog-level grant, everything else is enumerated per schema, and the repetition is the cost of putting environment in the schema name rather than an oversight. The M5/M7 mitigation is prevention — never grant `CREATE SCHEMA`, and restrict `CREATE TABLE` on unprefixed schemas to the build service principal — backed by six scheduled drift checks, because "we never granted that" is an intention until something asserts it. **All group names in the file are placeholders** and must be confirmed against `databricks account groups list --profile account-apfm`.

**Masking** ([11](ddl/11-pii-masking-prepared-not-applied.sql)). Prepared, entirely commented out. The deferral decision is not reopened. Three things to know before uncommenting are in the file header; the sharpest is that masks **break entity matching**, so a Genie agent tuned against an unmasked `dim_customer` must be re-tuned as part of the same change. One PII column escapes the schema isolation — `fact_invoice_line.ship_to_name` sits in a widely-granted schema, so the file 10 grant is not a backstop for it.

## Two corrections and one rename

These are places where writing the DDL forced a decision the design document left open or got wrong. Each is a change to the design of record, not a private deviation.

**AR aging history is reconstructable.** The initial plan implies today's open file cannot answer "what was aged 60+ last March," and treats a daily snapshot as the only route. It is not: `RM20201` and `RM30201` carry `DATE1`, `GLPOSTDT`, `APTODCDT`, `ApplyToGLPostDate` and `APPTOAMT`, so outstanding as of date `D` is the document amount less the applies dated on or before `D`. **The apply trail *is* the history.** `snap_ar_aging_daily` is still worth building — for cost, since the reconstruction is an expensive window over two unioned tables — but it is not load-bearing the way `snap_period_close_daily` is. `mart_ar_aging` therefore carries `computation_basis` (`snapshot` or `reconstructed`) *in its grain*, so both figures can coexist and a disagreement between them is visible rather than resolved by whichever ran last.

**Close state moved off `dim_fiscal_calendar`.** The design requires close state on the fiscal calendar and separately records that GP grains close on period **× series** — a period can be closed for Financial and open for Sales. Putting a series-grained attribute on a period-grained dimension is a grain violation, and a single close flag per period would be silently wrong for whoever cares about the other series. Close state lives entirely in `snap_period_close_daily`, with `vw_period_close_current` and `vw_period_close_transitions` for convenience. `mart_period_summary` consequently carries `financial_series_is_closed` and `sales_series_is_closed` as separate columns.

**`mart_trial_balance` → `mart_account_period_activity`**, tagged `design_slot='mart_trial_balance'` so the mapping back to the design is machine-readable. This *implements* the design rather than departing from it — the design says "name it for what it is or it will be reconciled against a real trial balance and lose." `includes_bbf` and `includes_pl_close` are part of its grain, and `mart_plan_vs_actual` inherits both, because a variance computed against an actual that includes beginning-balance-forward entries is wrong in a way that looks plausible.

## Deliberately absent

Named so that absence reads as a decision rather than an oversight.

- **`GL00105`** (account index master) — not replicated. `dim_gl_account` substitutes for it from `GL00100` + `SY00300` + `GL40200`.
- **`SOP30200`** (sales document header history) — not replicated, and load-bearing. No source-of-truth document date, document-level customer, void status, or document salesperson for an invoice. Each absence is labelled on the corresponding column in `fact_invoice_line`; `void_status` is kept as a permanently-null column so the gap is visible in the schema.
- **`sop30300` for CAPFM** — not replicated. `fact_invoice_line` covers APFM only, tagged `covers_legal_entities='APFM'`, so a cross-entity comparison does not read absence as zero.
- **Commitments / Purchase Order Processing** — no POP tables replicated. `mart_plan_vs_actual.committed_amount` exists and is always `NULL`, with the reason on the column. Populating it needs new ingestion, not new SQL.
- **Marketing spend, advisor cost, unit economics** — no spend source replicated. DTS-4188 / DTS-4180 territory. Out of scope, per the warning on [Mart Design](Mart%20Design.md).
- **`dim_partner`** — the conformed commercial counterparty does not exist yet. `dim_customer.partner_key` is present and nullable **without** a foreign key until it does, so the bridge is designed in rather than bolted on.

### Source columns excluded on purpose

Recorded in table tags (`excludes_source_columns`) so the exclusion cannot be quietly undone by someone adding "the rest of the columns."

| Column | Table | Why |
|---|---|---|
| `CRCRDNUM`, `CCRDXPDT`, `CRCARDID` | `RM00101` → `dim_customer` | Payment-card exposure, independent of the deferred-masking decision. No epic use case needs it |
| `PASSWORD` | `SY01400` → `dim_gp_user` | This dimension exists *so that* consumers resolving `LASTUSER` / `USWHPSTD` / `PSTUSRID` never read `sy01400` directly |
| `BUDPWRD` | `GL00200` → `fact_plan_amount` | A budget password. A secret that reaches a mart has been published |

Exclusion beats masking whenever the column has no analytic use.

## Before the first statement runs

1. **Choose the workspace.** `attivita` or production. Pass `--profile` explicitly either way.
2. **Confirm the group names** in [10-grants](ddl/10-grants.sql) against the account console. A grant to a similarly-named group that happens to exist succeeds silently.
3. **Start `snap_period_close_daily`** into a scratch schema. It does not need the catalog and it does not need Finance's review.
4. **`DESCRIBE` before promoting `dim_date`**, and confirm `date_key`'s type — every fact depends on it (T-01).
5. **Profile the IPR and CST tables.** Everything marked `PROFILE` in files 05 and 08 is a placeholder, not an assertion.
6. **Decide whether `dev_identity` / `qa_identity` get real PII.** The `finance-engineers` grant in file 10 is too wide if they do. This must be settled before the first load, not after.
